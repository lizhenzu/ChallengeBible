- 확정(사용자): 소속 탭 아래 "진급 보내기"와 같은 칸에 "반 바꾸기"(JS 없이), 참여자만 고름(같은 체크 칸), 새 반은 직접 쓰거나 기존 반에서 고름(빈칸 = 반 없음, 50자), 기록은 남기지 않음(반은 표시 · 필터용)
- `MemberAdminService.RegroupAsync`: 이 부서의 승인된 참여자만 바꾸고 나머지 번호는 건너뜀

### 콘텐츠 달력(`/{slug}/admin/content`) — 완료(feature/content-calendar), 1차는 보기만
- 확정(사용자): ① "우리 부서 것으로 바꾸기 (2차)" 버튼은 눌리지 않게 ② 지난 12달 ~ 다음 12달 ③ 경고: 14일 안 빈 칸 빨강, 그 뒤 빈 칸 · 초안 노랑, 관리 홈 "비어 있는 콘텐츠" 카드 → 그 날짜(카드 기준 7일 · 말씀 · 퀴즈는 그대로)
  ④ 우리 부서 것은 만든 사람 · 날짜 ⑤ 관리 메뉴 "콘텐츠"(관리자만) ⑥ 날짜 · 종류는 링크(서버가 다시 그림)
- 고르기는 미션 화면과 같다: 부서 공개본 → 공용 공개본 → 초안 → 없음. 기도 공용은 날짜 번호(0053), 암송 공용은 그해 몇째 주(0052). 새 마이그레이션 · 실DB SQL 없음

### 시즌(`/{slug}/admin/season`) — 완료(feature/season)
- 확정(사용자): ① 바꾼 기록은 AuditLog(Action `SeasonStart`) ② 다음 시즌 시작일은 언제든 미리 정함(다음 해 안) ③ 지난 시즌은 해마다 한 줄(시작일 · 참여한 사람 · 점수 합), 순위 화면은 나중
  ④ 빠른 고르기 = 그해 1월 1일 · 첫 주일(계산) ⑤ 관리 메뉴 "시즌"(관리자만)
- 늦출 때 빠지는 점수는 `?D=` 로 서버에서 계산해 보여 주고 "확인했어요" 체크 뒤에만 바꾼다. 시즌 점수는 원장에서 바로 계산하므로 다시 계산할 표가 없다. 새 마이그레이션 · 실DB SQL 없음

### 이름 · 색(`/{slug}/admin/branding`) — 완료(feature/branding)
- 확정(사용자): ① 대표 색은 부서 화면(홈 · 미션 · 내 점수 · 관리)의 `--accent` 에만, 통독 · 성경 본문 · 부서 밖 화면은 파랑(`<html data-color>`)
  ② 부서별 `/{slug}/manifest.webmanifest` · `/{slug}/icon.svg`(대표 색 바탕 + 짧은 이름 2자, PNG 는 나중) · theme-color, 로그인 없이 열림
  ③ 바꾼 기록은 `app.AuditLog`(Action `TenantBranding`, RLS 없는 표라 TenantId 로 직접 거름) ④ 관리 메뉴 "이름 · 색"(관리자만)
- 새 마이그레이션 · 실DB SQL 없음. 부서 화면 제목도 부서 앱 이름(0038)

#### 시작 전 조사(기록)
- 시안: `docs/design/시안/관리-이름색-단독시안.html` (입력: 앱 이름 30자 · 짧은 이름 12자 · 대표 색 4가지 | 미리보기 | 바꾼 기록). 규칙: ADR 0033 · 0038
- DB: `Tenant.AppName` · `AppShortName` · `ThemeColor` 열은 이미 있다. 새 마이그레이션 없이 화면 · 서비스만 만들면 된다
- 지금 코드에서 쓰이는 곳: 앱 이름은 `TenantContext.AppName`(부서 홈 제목 정도), 대표 색은 플랫폼 · 진급 · 참여 목록의 작은 표시뿐이다
- 시안과 다른 점(먼저 사용자와 정할 것):
  1. 대표 색이 부서 화면의 강조색(`--accent`)에 아직 적용되지 않는다 — 적용 범위를 정해야 한다
  2. 부서별 PWA 매니페스트(`/{slug}/manifest.webmanifest`, 0038 결정 5)가 없다 — 짧은 이름은 매니페스트가 있어야 의미가 있다
  3. "바꾼 기록"을 남길 곳이 없다 — `app.AuditLog`(진급 때 만듦)를 쓰면 된다
  4. 관리 메뉴에 "이름 · 색" 탭 추가
- 플랫폼 부서 관리에서도 이름 · 시간대 · 색을 고칠 수 있다(`PlatformTenantService`). 앱 이름은 플랫폼에서 안 고친다

진행 방식: 사용자는 한 단계씩 확인하며 진행한다("N단계 진행" / "네"). 단계마다 구현 → 테스트 → 화면 캡처로 시안과 비교 → 커밋 · push → 한국어로 보고 → 다음 단계 제안.

참고: 공용 콘텐츠 · 미션 데이터의 서버 입력은 사용자가 플랫폼 화면에서 한다. `git stash` 에 "stale working copy…" 한 건이 남아 있다(예전 작업 폴더 복사본, 필요 없으면 `git stash drop`).
남은 원격 브랜치는 모두 main 에 합쳐졌다(`feature/promotion`, `feature/join-list`, `docs/mockup-comment-cleanup` 등). 새 작업은 main 에서 `feature/…` 로 시작한다.

## 5. 알아 두면 시간 아끼는 것

- 셸 명령에 한글을 넣으면 실패할 수 있다 → 한글은 파일 편집 도구로 쓰고, 셸 명령은 영어로만.
- Razor 에서 `@Model.X일` 처럼 한글이 바로 붙으면 이름으로 읽힌다 → `@(Model.X)일`. 조사는 `Ui.IGa(...)`.
- 한글이 HTML 에서 이스케이프되지 않게 `WebEncoderOptions` 를 `UnicodeRanges.All` 로 해 두었다.
- 날짜 표기는 `"M'/'d"` (ko 문화권 구분자가 `-`).
- 점수 값은 코드에 쓰지 않고 RuleSet 에서 읽는다. DB 의 GETDATE() 금지. TenantId 없는 조회 금지.
- 콘텐츠 수정: 공개된 것은 새 개정을 만들고 이전 것은 보관, 초안은 그 자리에서 수정. 퀴즈는 초안 저장 → 보기 추가 → 상태 지정(CK_DailyQuiz_Correct).
- 실DB 에 SQL 로 직접 쓸 때는 먼저 `EXEC sp_set_session_context N'PlatformScope', 1;` — 안 하면 RLS 때문에 0건 처리되거나 FK 오류만 난다.
- 마이그레이션 적용은 `dotnet ef migrations script <이전> <다음> --idempotent` 로 SQL 을 만들어 실행한다. 만든 파일 맨 앞 BOM 과 `GO` 를 지워야 SQL Studio 에서 오류가 없다. 새 열을 같은 묶음에서 쓰는 데이터 변환은 `EXEC(N'...')` 로 감싼다.
- 다중 줄 CHECK 제약 SQL 은 `.ReplaceLineEndings("\n")` — Git 이 CRLF 로 체크아웃하면 모델이 바뀐 것으로 보여 쓸데없는 마이그레이션이 생긴다.
- 이 PC 의 git 은 옛 버전(`git switch`, `git branch --show-current` 없음) → `git checkout -b`, `git rev-parse --abbrev-ref HEAD`. `gh` 도 없어서 머지는 로컬 `--no-ff` 후 push.
- DB 를 바꾼 배포는 **SQL 적용 → `publish/web` 업로드** 순서(거꾸로 하면 새 열이 없어 오류).
