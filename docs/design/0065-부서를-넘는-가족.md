# 0065. 부서를 넘는 가족(제안)

- 상태: **제안** (2026-10-25, 사용자 요청 "부서를 초월한 가족팀 구성 · 모든 포인트 합산") — 아래 "결정할 것"을 사용자와 하나씩 정한 뒤 확정
- 바꾸는 대상: **D12 · 0012**(가족팀은 같은 영역 안에서만), **0046**(부모는 가족과 함께할 부서 하나), R-90 ~ R-97, R-168
- 관련: D20(테넌트 격리), 0029 · 0040(통독은 계정 단위), 0064(임시 부서), 보호자 다시 설계(나중에 할 일 5)

## 맥락
지금 가족팀은 **부서(영역) 안의 물건**이다. 팀 · 구성원 · 단계 기록이 모두 TenantId 를 가지고, 구성원은 그 부서의 참여자만 될 수 있다.
그래서 첫째가 유년부, 둘째가 초등부, 엄마가 장년 통독모임이면 한 가족이 한 팀이 될 수 없다.
0046 은 이를 피하려고 "부모는 한 부서만 고른다"는 우회를 두었지만, 형제가 다른 부서인 문제는 그대로다.

사용자가 원하는 것: **플랫폼에 있는 사람이면 부서와 상관없이 서로 가족으로 묶고, 가족 모두의 점수를 합쳐서 본다.**

## 제안

### 1. 개념: "가족"은 부서 위, 계정끼리 묶는다
- 가족(Family)은 **어느 부서에도 속하지 않는다.** 계정(Account)처럼 플랫폼에 하나씩 있는 물건이다.
- 구성원은 **참여자가 아니라 계정**이다. 그래서 어느 부서에 있든, 여러 부서에 있든 한 가족이 될 수 있다.
- 한 계정은 **한 가족에만** 들어간다.
- 용어: 부서 안의 "가족팀"을 없애고 **"가족"**으로 부른다(02 용어집 고침). 화면 글자는 "우리 가족".

### 2. 누가 만들고 어떻게 들어오나: 가족끼리 직접(초대 코드)
- 아무 계정이나 **[가족 만들기]** → 그 사람이 **가족 대표**(나중에 넘길 수 있음).
- 가족마다 **초대 코드 · 초대 주소**가 있다(예: `/family/join?code=K7Q2M9`). 대표가 카톡 등으로 보낸다.
- 받은 사람은 로그인한 채로 주소를 열고 **[이 가족에 들어가기]** — 본인이 눌러야 들어간다(남을 몰래 넣지 못함).
- 대표는 구성원을 **빼기**, 관계(학생 · 엄마 · 아빠 · 할머니 · 할아버지 · 기타) · 순서 정하기, 초대 코드 **새로 만들기**(이전 코드는 못 씀)를 할 수 있다.
- 구성원은 언제든 **나가기**.
- 부서 관리자는 가족을 만들거나 고치지 않는다(부서를 넘는 일이라 부서 권한 밖). 플랫폼 관리자는 문의 대응용으로 보기 · 정리만.

### 3. 점수: 구성원 모두의, 모든 부서의 미션 점수를 합친다
- **가족 점수 = 구성원 각자가 모든 부서에서 얻은 미션 점수의 합.** (통독은 점수가 없어서 빠진다 — 진도율만 있음)
- 기간: 부서마다 시즌 시작일이 달라서(D17) 가족은 **달력 해(1월 1일 ~ 12월 31일, 미션 날짜 기준)**로 센다. 해마다 0부터.
- 가족 단계(1,000 · 2,000 · … 축하 · 박수, R-96)와 축하 카드(R-97)는 그대로, 가족 기준으로.
- 가족이 되기 **전** 점수도 그해 것이면 합산에 들어간다(가족을 언제 만들었는지와 상관없이 "올해 우리 가족이 모은 점수").
- 진급(D16 · D22)으로 이전 부서 기록이 지워지면 합산에서도 빠진다 — 지금과 같다.

### 4. 격리(D20)를 지키는 방법
- 가족 표(`Family`, `FamilyMember`, 단계 기록)는 **TenantId 가 없는 플랫폼 표**다(계정 표와 같은 취급). 읽고 쓰기는 늘 "내 계정이 구성원인 가족"으로 거른다.
- 부서를 넘어 점수를 모으는 일은 **시스템 연결(ISystemDb)을 쓰는 지정 처리 하나**(`FamilyScoreService`)만 한다(물리 설계 3-3 에 올림).
  - 돌려주는 것은 **구성원별 합계 점수 · 마지막 참여일 · 부서 이름**뿐. 다른 부서의 수행 기록 · 달력 · 반 · 다른 아이들은 보이지 않는다.
- 부서 관리자는 자기 부서 사람이 어느 가족인지, 가족 합계만 볼 수 있다(다른 부서 구성원 이름은 안 보임 — 결정할 것 ③).

### 5. 화면(시안은 확정 뒤 따로)
| 화면 | 내용 |
|---|---|
| **우리 가족** `/account/family`(지금 보호자용 화면 자리를 다시 씀) | 가족 이름 · 올해 가족 점수 · 다음 단계까지, 구성원 카드(이름 · 관계 · 부서 · 올해 점수), 초대 코드 · [초대 주소 복사], 대표면 빼기 · 순서 · 관계 |
| 가족 없을 때 | [가족 만들기] · "초대 주소를 받았으면 그 주소를 눌러 주세요" |
| 초대 받기 `/family/join?code=` | 가족 이름 · 대표 이름 · 지금 구성원 수 → [이 가족에 들어가기] |
| 부서 홈 "우리 가족" 칸 | 가족 점수 · 단계 · 축하 카드(지금 칸을 가족 기준으로) |
| 순위 "가족" 탭 | 결정할 것 ③ |
| 부서 관리 > 가족팀 | 없앤다(또는 "우리 부서 사람의 가족" 보기만) |
| 플랫폼 > 가족 | 찾기 · 보기 · 문의 대응(빼기 · 해체) |

### 6. 지금 것을 어떻게 정리하나
- 부서 안 가족팀(`FamilyTeam` · `FamilyMember` · 단계 기록, 모두 TenantId) → **새 가족으로 옮긴다**: 팀 하나 = 가족 하나, 구성원 참여자 → 그 계정, 팀을 만든 관리자 대신 **첫 어른 구성원(없으면 첫 구성원)을 대표**로. 한 계정이 두 부서 팀에 있었으면 결정할 것 ⑤.
- 0046 의 "가족과 함께할 부서"(`Account.FamilyTenantId`) — 가족이 부서와 무관해지면 쓸모가 없어진다 → 결정할 것 ④.
- 기능 스위치 `Features.FamilyTeam`(지금 플랫폼 규칙 하나) → 이름만 "가족"으로, 꺼지면 가족 화면 · 합산 전부 숨김.
- 임시 부서(0064)에서 순위 · 가족팀을 끄던 것 → 가족은 부서와 무관하니 **임시 부서 사람도 가족에 들어갈 수 있다**(점수는 승인 때 부서로 옮겨지므로 합산은 그대로).

### 7. 데이터(논리 설계 초안)
```
Family            Id, Name?, InviteCode(8, 고유), OwnerAccountId, IsActive, CreatedUtc
FamilyMember      Id, FamilyId, AccountId, Relation, SortOrder, JoinedUtc, LeftUtc?
                  고유: 활성(LeftUtc IS NULL) AccountId 하나 → 한 계정 한 가족
FamilyMilestoneReached / FamilyMilestoneDismiss   (FamilyId, Year, Threshold) — TenantId 빠짐
```
- 합산 쿼리(시스템 연결): 구성원 AccountId → Membership → Participant → 점수 장부(그해 날짜) 합계, AccountId 별로 묶음.
- 감사 기록: 가족 만들기 · 들어오기 · 나가기 · 빼기 · 코드 새로 만들기 · 대표 넘기기.

### 8. 진행 순서(06 문서 단계)
1. 이 제안의 "결정할 것"을 하나씩 정함 → 이 문서 확정, D12 · 0046 · R-90 ~ R-97 · R-168 고침
2. 도메인 모델 · 논리 · 물리 설계, 옮기기 SQL(기존 가족팀 → 가족)
3. 시안: 우리 가족 · 초대 받기 · 부서 홈 칸 · (순위 탭)
4. 구현 + R-번호 테스트(격리: 다른 부서 기록이 새지 않는지 테스트 포함)
5. 실DB: 마이그레이션 → 옮기기 → 게시 → 라이브 확인
