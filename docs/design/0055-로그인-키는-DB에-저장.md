# 0055. 로그인 쿠키를 푸는 키는 DB 에 둔다 — 게시해도 로그인 유지

- 상태: 확정 (2026-10-24, 사용자 요청)
- 관련: 0011(SmarterASP), 0050(이메일 로그인), 물리 설계 5(마이그레이션과 배포)

## 배경
게시할 때마다 모든 사용자가 다시 로그인해야 했다. 로그인 쿠키(`cb.auth`, 30일)는 ASP.NET Core Data Protection 키로 암호화되는데,
SmarterASP(IIS, 사용자 프로필 없음)에서는 키가 메모리에만 있어 게시 · 앱 재시작 때마다 새 키가 생기고 이전 쿠키를 풀 수 없었다.

## 결정
1. 운영(개발 외 환경)은 Data Protection 키를 DB 표 `app.DataProtectionKey` 에 둔다(`PersistKeysToDbContext`).
   사이트 폴더(App_Data 등)는 게시 방식에 따라 지워질 수 있어 쓰지 않는다.
2. 이 표는 영역 데이터가 아니다 — TenantId · RLS · 전역 필터 없음(Data Protection 이 읽고 쓰는 시스템 표).
   표는 AppDbContext 마이그레이션 `DataProtectionKeys` 가 만들고, 읽고 쓰는 것은 웹의 `KeyStoreDbContext` 만 한다.
3. 응용 이름은 `ChallengeBible` 로 고정한다(사이트 경로가 바뀌어도 같은 키를 쓴다).
4. 개발 · 테스트는 기본값(사용자 프로필 폴더)을 그대로 쓴다.

## 결과
- 적용: `tools/sql/migrate-DataProtectionKeys.sql` 실행 → 게시. 적용 직후 한 번은 다시 로그인해야 하고, 그 뒤로는 게시해도 유지된다.
- 키는 90일마다 새로 만들어지고 옛 키도 표에 남아 기존 쿠키를 계속 푼다. 행은 몇 개뿐이다.
- 키는 암호화하지 않고 저장된다(공유 호스팅에 인증서 · DPAPI 사용자 프로필 없음). DB 접근 권한이 곧 쿠키 위조 권한이므로 접속 문자열은 지금처럼 Git 밖에 둔다.
