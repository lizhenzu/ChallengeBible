# 물리 설계 (초안)

- 상태: 초안 (2026-10-22)
- 기준: [논리 설계](논리-설계.md), ADR 0007 · 0018 · 0020 · 0030
- 참조 DDL: [물리-설계.sql](물리-설계.sql) — **설계 확인용**이다. 실제 DB 는 EF Core 마이그레이션으로 만든다(5절).
- 대상: SQL Server 2019 이상 (SmarterASP 새 DB, 0021)

## 1. 형식 규칙

| 논리 | SQL Server | 비고 |
|---|---|---|
| 정수 키 | `int IDENTITY` | 많이 쌓이는 표(Activity, QuizAttempt, PointLedger, Outbox, AuditLog)는 `bigint IDENTITY` |
| 문자열 | `nvarchar(n)` | 코드 · 영역 코드 · 유튜브 ID 처럼 영문만 쓰는 값은 `varchar(n)` |
| 코드 | `varchar(20~40)` + `CHECK (… IN (…))` | 허용 값을 DB 가 검사 |
| 날짜 | `date` | 영역 시간대 기준 날짜 |
| UTC 시각 | `datetime2(3)` | 열 이름은 `…Utc` |
| 참거짓 | `bit` | |
| JSON | `nvarchar(max)` + `CHECK (ISJSON(…) = 1)` | |

- **기본값에 현재 시각 함수(`GETDATE()`, `SYSUTCDATETIME()` 등)를 쓰지 않는다.** 모든 시각은 앱이 넣는다(X-09).
- 스키마: 업무 표는 `app`, 격리 함수 · 정책은 `sec`.

## 2. 인덱스 규칙

- 영역 범위 표: 기본 키 `Id` 는 **비클러스터**, **클러스터 인덱스는 `TenantId` 로 시작**한다(T-4).
  - 보통은 `(TenantId, Id)` 고유 클러스터 — 복합 외래 키(T-3)의 대상도 된다.
  - 조회 패턴이 뚜렷한 표는 그 순서로 클러스터: Activity · PointLedger `(TenantId, ParticipantId, MissionDate)`, DailyPoint `(TenantId, ParticipantId, Date)`. 이 경우 `(TenantId, Id)` 는 비클러스터 고유로 따로 둔다.
- 순위: SeasonPoint `(TenantId, Year, TotalPoints DESC)` — 한 번 읽어 순위 화면을 만든다(X-03).
- 조건부 고유(필터 고유 인덱스)
  - 콘텐츠 날짜: `(TenantId, ExposeDate) WHERE IsCurrent = 1` — 공용(NULL)도 날짜당 1건(고유 인덱스에서 NULL 은 같은 값으로 취급)
  - Activity: 말씀 · 기도 · 퀴즈 `(TenantId, ParticipantId, MissionDate, MissionItem) WHERE MissionItem <> 'Recite'`, 암송 `(TenantId, ParticipantId, ReciteStartDate) WHERE MissionItem = 'Recite'`
  - FamilyMember `(TenantId, ParticipantId) WHERE IsActive = 1`
  - PromotionRequest `(AccountId, SourceTenantId) WHERE Status = 'Pending'`

### 논리 설계에서 바꾼 점
- **Activity 의 콘텐츠 참조**를 종류별 열 4개(DailyWordId · DailyPrayerId · DailyQuizId · WeeklyVerseId)로 나눴다. 각 열에 외래 키를 걸고, MissionItem 과 맞는 열 하나만 값이 있도록 CHECK 한다.
- **암송 주 1회 고유**를 콘텐츠 행 ID 가 아니라 **그 주의 시작일(ReciteStartDate)** 로 건다.
  콘텐츠를 고치면 새 개정 행이 생기므로(R-124), 행 ID 로 걸면 같은 주에 한 번 더 암송할 수 있게 되기 때문이다.
- 콘텐츠 하위 표(질문 · 영상 · 보기 · 허용 답)에도 `TenantId`(NULL 가능)를 둔다. RLS 가 하위 표에도 같은 조건을 걸 수 있게 하기 위해서다.
- **DailyPoint.TotalPoints** 는 네 점수의 합을 계산 열(PERSISTED)로 둔다 — 합이 어긋날 수 없다.

## 3. 격리 — RLS (0007, 0018, 0020)

### 3-1. 세션 값
앱은 연결을 열 때마다(EF Core 연결 가로채기) `sp_set_session_context` 로 아래 값을 **읽기 전용(`@read_only = 1`)** 으로 넣는다.
한 번 넣으면 그 연결에서는 바꿀 수 없다.

| 키 | 값 | 넣는 곳 |
|---|---|---|
| `TenantId` | 주소의 영역 코드로 찾은 영역 Id | 영역 화면 요청 |
| `AccountId` | 로그인 계정 Id | 로그인한 모든 요청 |
| `PlatformScope` | 1 | **시스템 연결만**(3-3) |

연결 풀이 연결을 돌려쓸 때 세션 값은 초기화된다. 이것을 통합 테스트로 확인한다(다른 영역 요청이 이전 값을 물려받지 않음).

### 3-2. 조건 함수와 정책
| 함수 | 통과 조건 | 쓰는 표 |
|---|---|---|
| `sec.fn_Tenant(TenantId)` | `= 세션 TenantId` 또는 PlatformScope | 영역 범위 표 전부 (읽기 · 쓰기) |
| `sec.fn_Membership(TenantId, AccountId)` | 위 조건 또는 `AccountId = 세션 AccountId` | Membership 읽기 — "내 소속 영역 목록"(R-135) |
| `sec.fn_SharedRead(TenantId)` | `TenantId IS NULL` 또는 fn_Tenant | 콘텐츠 표 읽기 |
| `sec.fn_SharedWrite(TenantId)` | `TenantId IS NULL` 이면 PlatformScope 만, 아니면 fn_Tenant | 콘텐츠 표 쓰기 |
| `sec.fn_Account(AccountId)` | `= 세션 AccountId` 또는 PlatformScope | VerseReadMark, Bookmark (0029) |
| `sec.fn_Promotion(Source, Target)` | 둘 중 하나가 세션 TenantId, 또는 PlatformScope | PromotionRequest |

- 읽기는 FILTER 조건(안 보임), 쓰기는 BLOCK 조건(AFTER INSERT · AFTER UPDATE — 다른 영역 값으로 넣거나 바꾸면 오류).
- 플랫폼 표(Account, Tenant, 성경, 퀴즈 문제 은행, 플랫폼 규칙, 감사 로그)에는 RLS 를 걸지 않는다. 쓰기 권한은 앱의 정책으로 막는다.
- 앱 전역 필터(EF Core)는 같은 조건을 C# 으로 한 번 더 건다(0020).

### 3-3. 시스템 연결 (PlatformScope)
영역 조건을 넘는 일은 **시스템 연결**로만 한다. 시스템 연결은 별도 DbContext 팩토리 하나에서만 만들고, 아래 처리기만 쓴다.

| 처리기 | 이유 |
|---|---|
| 진급 승인 (0026, 0030) | 새 영역 소속 활성화 + 이전 영역 삭제를 한 트랜잭션으로 |
| 성경 읽음 초기화 (0029) | 영역 관리자가 다른 계정의 계정 범위 데이터를 지움 |
| 비밀번호 임시 초기화 (0035) | 대상 계정의 다른 영역 역할(관리자 여부)을 확인 |
| 플랫폼 관리 화면 | 영역 목록 · 사용량 · 공용 콘텐츠 작성 |
| 아웃박스 발송기 | 모든 영역의 미발송 이벤트 |

- 각 처리기는 시작 전에 앱에서 권한을 검사하고, 실행 사실을 AuditLog 에 남긴다.
- 0030 의 "이전 영역 테넌트 컨텍스트로 전환"은 이 시스템 연결로 구현한다.
- 테스트: 일반 요청 경로의 코드가 시스템 팩토리를 참조하지 않는지 아키텍처 테스트로 검사한다.

## 4. DB 가 직접 지키는 규칙

| 규칙 | 방법 |
|---|---|
| 하루 · 항목당 1건 (R-61, X-04) | Activity 필터 고유 |
| 암송 주 1회 (R-51) | Activity 필터 고유 (ReciteStartDate) |
| 퀴즈 시도 번호 중복 없음 | QuizAttempt 고유 |
| 원장 한 기록에 한 줄 | PointLedger 고유 (ActivityId) |
| 콘텐츠 날짜당 1건 (R-121, X-18) | 콘텐츠 필터 고유 |
| 암송 기간 안 겹침 (R-121) | **트리거** `app.trg_WeeklyVerse_NoOverlap` — 같은 소유의 현재 개정끼리 기간이 겹치면 롤백 |
| 다른 영역 참조 금지 (T-3) | 복합 외래 키 |
| 퀴즈 정답 보기는 그 퀴즈의 보기 | 복합 외래 키 (CorrectChoiceId, Id) → (Id, DailyQuizId) |
| 시즌 시작일은 그해 날짜 (0028) | CHECK |
| 구절 범위 끝 ≥ 시작 | CHECK |

앱에서 지키는 규칙(규칙 값에 따라 달라서 DB CHECK 로 쓸 수 없음): 인정 기간, 퀴즈 시도 상한, 항목 사용 여부, 시즌 시작일 전 차단, 점수 값.

## 5. 마이그레이션과 배포 (X-22)

- 표 · 인덱스 · 제약은 **EF Core 마이그레이션**으로 만든다. 참조 DDL 과 이름 · 형식을 맞춘다.
- EF 가 만들지 못하는 것(RLS 함수 · 정책, 트리거, 계산 열 세부)은 마이그레이션 안의 `migrationBuilder.Sql(...)` 로 넣는다.
- 트리거가 있는 표는 EF 설정에 `HasTrigger` 를 적는다(EF 의 저장 방식이 트리거와 맞게 바뀜).
- **앱 시작 시 자동 마이그레이션 금지.** 배포 때 `dotnet ef migrations script --idempotent` 로 SQL 을 만들어 확인한 뒤 SmarterASP DB 에 실행한다.
- 접속 문자열은 Git 에 두지 않는다(X-21). 개발은 사용자 비밀(user-secrets), 운영은 호스팅 환경 설정.

## 6. 남은 확인 (구현 · 배포 단계에서)

- SmarterASP DB 의 기본 데이터 정렬(collation): 아이디 비교가 대소문자를 구분하지 않는지 확인. 구분하면 LoginId 에 대소문자 무시 정렬을 지정한다.
- SmarterASP 계정 권한으로 `CREATE SECURITY POLICY` 실행이 되는지 첫 배포 전에 빈 DB 로 확인.
